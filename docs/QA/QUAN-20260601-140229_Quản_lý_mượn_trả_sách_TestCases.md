**TEST SPECIFICATION**

**1. Introduction**

This document outlines the test specification for the "Quản lý mượn trả sách" (Loan Management) feature within the ONENET system. The purpose of this feature is to allow librarians to manage the borrowing and returning of books by readers, including creating new loan requests, recording book returns, and viewing loan history with various filters.

*   **Feature ID:** QUAN-20260601-140229
*   **Feature Name:** Quản lý mượn trả sách
*   **BRD PR#:** 9
*   **SRS PR#:** 10
*   **DEV PR#:** 15

**2. Test Items**

The following components/APIs related to the "Quản lý mượn trả sách" feature will be tested:

*   **API Endpoint:** `POST /api/v1/Loans` (Create Loan)
*   **API Endpoint:** `PUT /api/v1/Loans/{loanDetailId}/return` (Record Book Return)
*   **API Endpoint:** `GET /api/v1/Loans` (Get Loans)
*   **Commands:** `CreateLoanCommand`, `RecordBookReturnCommand`
*   **Queries:** `GetLoansQuery`
*   **Validators:** `CreateLoanCommandValidator`, `RecordBookReturnCommandValidator`, `GetLoansQueryValidator`
*   **Entities:** `PhieuMuon`, `ChiTietPhieuMuon`, `Reader`, `Book` (interactions)
*   **Database Interactions:** Data persistence and updates for `PhieuMuon`, `ChiTietPhieuMuon`, `Book` quantities.

**3. Features to be Tested**

This test specification covers the following functional requirements derived from the provided DEV PR Diff:

*   **FR_LOAN_001: Tạo phiếu mượn sách:**
    *   Người dùng (Thủ thư) có thể tạo phiếu mượn mới cho độc giả.
    *   Hệ thống phải kiểm tra độc giả tồn tại và hợp lệ (đang hoạt động, chưa hết hạn).
    *   Hệ thống phải kiểm tra số lượng sách độc giả đang mượn không vượt quá giới hạn (tối đa 5 cuốn tổng cộng).
    *   Hệ thống phải kiểm tra sách tồn tại và có đủ số lượng trong kho.
    *   Hệ thống phải tạo phiếu mượn và các chi tiết phiếu mượn tương ứng.
    *   Hệ thống phải giảm số lượng tồn kho của các cuốn sách đã mượn.
    *   Hệ thống phải ghi nhận ngày mượn (hiện tại) và ngày hẹn trả (14 ngày sau).
*   **FR_RETURN_001: Ghi nhận trả sách:**
    *   Người dùng (Thủ thư) có thể ghi nhận việc trả sách cho một chi tiết phiếu mượn cụ thể.
    *   Hệ thống phải kiểm tra chi tiết phiếu mượn tồn tại và chưa được trả trước đó.
    *   Hệ thống phải kiểm tra sách tương ứng với chi tiết phiếu mượn tồn tại.
    *   Hệ thống phải cập nhật ngày trả thực tế và trạng thái chi tiết phiếu mượn thành "DaTra".
    *   Hệ thống phải kiểm tra và ghi nhận trạng thái quá hạn (`IsQuaHan`).
    *   Hệ thống phải tăng số lượng tồn kho của cuốn sách đã được trả.
    *   Hệ thống phải cập nhật trạng thái của phiếu mượn cha thành "DaTraHoanTat" nếu tất cả các chi tiết phiếu mượn trong phiếu đó đã được trả hết.
*   **FR_VIEW_001: Xem danh sách phiếu mượn:**
    *   Người dùng (Thủ thư/Độc giả) có thể truy vấn danh sách các phiếu mượn.
    *   Hệ thống phải hỗ trợ lọc phiếu mượn theo ID độc giả.
    *   Hệ thống phải hỗ trợ lọc phiếu mượn theo trạng thái quá hạn (`IsOverdue`).
    *   Hệ thống phải hỗ trợ phân trang (`PageNumber`, `PageSize`).
    *   Hệ thống phải trả về thông tin chi tiết của phiếu mượn bao gồm tên độc giả và tên sách.

**5. Approach**

*   **Testing Types:** Functional Testing, API Testing, Boundary Value Analysis, Negative Testing, Security Testing (Authentication/Authorization).
*   **Methodology:** Black-box testing, focusing on API endpoints and their responses based on the business rules.
*   **Test Case Design:** Test cases will be designed using a combination of equivalence partitioning, boundary value analysis, and error guessing techniques to ensure comprehensive coverage.
*   **Test Steps Format:** All test steps and expected results will follow the BDD (Given-When-Then) format.
*   **Test Data:** Specific test data will be prepared and outlined for each scenario group to ensure test repeatability and isolation.

**6. Item Pass/Fail Criteria**

*   **Pass:**
    *   API returns the expected HTTP status code (e.g., 200 OK, 201 Created, 400 Bad Request, 404 Not Found).
    *   API response body matches the expected data structure and content.
    *   Database state changes (e.g., `Quantity` of book, `TrangThaiPhieuMuon`, `TrangThaiChiTiet`, `IsQuaHan`) are correct.
    *   Validation rules are enforced correctly.
    *   Security rules (authentication/authorization) are enforced.
*   **Fail:**
    *   Any deviation from the "Pass" criteria.
    *   Unexpected errors or exceptions.
    *   Performance degradation (though not primary focus, noticeable slowness would be flagged).

**7. Suspend/Resumption Criteria**

*   **Suspend:** Testing will be suspended if critical bugs (blocking issues, system crashes, data corruption) are found that prevent further execution of related test cases.
*   **Resumption:** Testing will resume after critical bugs are fixed and verified by the development team, and a new build is deployed.
